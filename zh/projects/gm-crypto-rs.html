是什么

gm-crypto-rs 用纯 Rust 实现 {% include glossary-term.html term="sm2" %} 签名、加密与密钥交换（GB/T 32918）、 {% include glossary-term.html term="sm3" %} 哈希（GB/T 32905），以及 {% include glossary-term.html term="sm4" %} 分组密码（GB/T 32907）。 核心采用 {% include glossary-term.html term="no_std" %} + alloc，能编译到 wasm， 适配 RustCrypto 的 digest、mac、cipher 和可选的 aead 0.6 trait；v1.13.0 提供 112 个 C ABI 入口。

SM4 模式包括 GCM、CCM 和 XTS。CCM 加密要求调用方在构造时承诺明文总长度，随后按块输入； 解密支持增量输入，但输出一直缓冲到认证成功才交付。严格 DER 的 X.509 v3 解析与 SM2 签名验证 （GM/T 0015 profile；解析器不做信任判定），加上密钥派生、 记录层保护和证书对 / 证书链验证，组成 TLCP 工具集。协议状态与对端身份检查由调用方负责。

未经独立安全审计。下面的公开测试与时序测量都有适用边界，不能当作安全认证或常量时间证明。

固定在公开提交上的示例 是面向使用者的示例与冒烟测试导览，覆盖散列、签名与验签、加解密、密钥交换和编码。 它依赖 gmcrypto-core = "=1.11.2"，展示的是这一旧版本的能力，而非 v1.13.0。

要解决的问题

国密这几个算法，Rust 社区其实早有实现，写得好的那些，本来也都按常量时间设计——处理密钥的那段代码，跑多久跟密钥无关，免得别人靠测耗时反推出密钥。

难点在于，这种「常量时间」常常只在代码评审那一刻成立；之后随便一次重构、新加一条快路径、一次依赖升级，时序泄漏都可能悄悄溜回来，当场没人发现。这个库偏偏又卡在一堆容易让它松动的约束里：要逐字节对上 GB/T 标准、核心要能跑在 no_std / wasm 上、涉密路径在每次发版之间都得把关{% include glossary-term.html term="constant-time" %}，还要通过一层 C ABI 把这些路径暴露出来，供 C、C++、Go、Zig、Python 调用。

因此，这个库要解决的是：怎样在每次提交后检测时序回归，并在发版前作出判断。

约束与关键决策

持续测量。dudect-bencher harness 覆盖 20 条实际涉密路径。 其中 16 条带构建门禁，通常要求 |τ| ≤ 0.20。 只有 CBC 解密扇出在 EPYC 9V74 runner 上采用 0.55 阈值；其他 CPU 仍用 0.20。harness 报的是检测事件：统计量低只说明在当前测量预算下没检测到泄漏，不能证明泄漏不存在。 代价：每个 PR 都要付出测量开销；通过门禁也证明不了常量时间。

把门禁覆盖范围写清楚。16 条带门禁的路径覆盖 SM2 标量乘、签名、解密与密钥交换； SM4 密钥扩展、加密、CTR、CBC 解密扇出、GCM / CCM 解密、缓冲式 GCM 解密与 XTS 解密； 加密 PKCS#8 解密；以及 TLCP CBC 记录层解保护。 另外 4 条诊断——两条域求逆、k-class 签名与 HMAC-SM3——在 PR 上只做遥测， nightly 用 0.55 粗回归哨兵值监视。 noise_twin_class_split 是单独的、不拦截构建的噪声诊断，每轮必须有测量记录； 它不是第 21 条实际涉密路径。 代价：这套测量分层和不同 runner 的噪声都需要持续校准。

核心禁止 unsafe，SIMD 单独按需开。 gmcrypto-core 在 [lints] 表里禁掉了 unsafe （unsafe_code = "forbid"）——整个核心一行 unsafe 都不许有。可位切片 SIMD 的 S-box 偏偏离不开 unsafe，于是把它整段挪进单独的 gmcrypto-simd crate，用时再通过 sm4-bitsliced-simd 特性打开。代价：快路径不是默认值——你得自己去开 SIMD，否则开箱跑的是更慢的线性扫描 S-box。

算术按常量时间设计，但前提写在明处。涉密的大数运算搭在 subtle 和 crypto-bigint 之上，密钥材料在 Drop 时由 zeroize 尽力抹零。v1.13 把这项处理扩到整个 SM4 流式类型家族，包括缓冲的载荷。整体是奔着常量时间设计的，但有些地方确实做不到。代价：在那些「乘法耗时跟操作数有关」的 CPU 上（部分较老的 x86、部分嵌入式芯片），这些时序性质并不成立——这一条我明写在「它不是什么」里，没藏着掖着。

把核心与 C 接口的调用契约写明。CCM 加密先承诺总长度再接收分块； 输入超量会让加密器进入失效状态，输入不足则不能生成有效的最终标签。解密在标签验证通过前不交付明文。 v1.13 新增的 8 个 C 函数遵守同样的契约。 代价：调用方必须提前知道明文长度，解密需要缓冲输出，Rust 与 C 的行为也必须一起测试。

证据

标准 KAT 向量、GmSSL 3.2.0 互操作检查和 OpenSSL 3.x SM4-XTS 比对 （xts_standard=GB）检验字节一致性。公开的 {% include glossary-term.html term="dudect" %} harness 检查时序回归， 35 个 cargo-fuzz 目标每晚覆盖不可信输入的解码 / 解密路径。 v1.13.0 C 头文件 可核对 CCM 调用契约与 112 个函数入口； 标签中的工作流 可核对特定 runner 的阈值与诊断分层。

一次时序失败拦下了发版

v1.11.1 第一次准备发布时，串行 SM4 修复让 TLCP CBC 的残余时序问题超过了门禁阈值，发版因此暂停。 SM3 压缩次数虽然相同，缓冲复制和填充分支却仍取决于秘密片段长度。补丁把内层 HMAC 改成固定执行流程后才发布。 这项修复影响所有启用 tlcp 的构建，包括 gmcrypto-c； 默认 gmcrypto-core 不启用这两项受影响特性，行为与时序均和 v1.11.0 相同。 另一项串行 SM4 修复只在启用 sm4-bitsliced-simd 时执行；吞吐提升只在 AArch64 上实测， x86_64 有正确性、KAT 与模糊测试覆盖，但没有吞吐测量。API、ABI 和线上字节格式均未变化。 标签中的修复记录 展示了门禁如何改变发版决定，并不能证明常量时间。

再补两条，专门针对「常量时间」这个说法——也是最容易嘴上说、最难证明的部分：

  • 门禁不是摆设：专门放一个故意泄漏时序的 negative_control，dudect 必须把它揪出来，否则 CI 直接失败（ timing_leaks.rs:167 ↗）。
  • 也说得老实：这套 harness 只能检测泄漏，并不能证明常量时间（ README.md:76 ↗）。

有四篇笔记展开证据边界：CI 门禁是怎么接线的、为什么值得展示的是负控制，而不是那排绿勾、把字节一致性当作互操作测试，以及把 unsafe 变成显式选择。

下一步

当前没有下一条路线定到具体版本。AVX-512 的 sbox_x64 仍在搁置的待办中。 端点身份绑定永久留给调用方，不属于延期实现的功能。

它不是什么

  • 不是 TLS / TLCP 协议栈——tlcp 这部分是一套原语工具集（密钥派生、记录层保护 / 解保护、链与证书对验证）。没有握手状态机、没有协商、也没有会话管理：协议要由调用方自己驱动，v1.9 的 C 示例就是这么做的。
  • 不是端点身份认证——verify_chain / verify_pair 只建立证书结构上的信任。把验证过的证书链绑定到具体的对端身份（相当于 TLCP 里的主机名验证）永远是调用方的事。
  • 不包括 SM9、ZUC、后量子算法。
  • 不是 HSM / SDF / SKF 集成。
  • 不是通过美国联邦信息处理标准（FIPS）或其他项目认证的密码模块。
  • 在乘法耗时跟操作数有关的 CPU 上（部分较老的 x86、部分嵌入式），不是常量时间的。

个人项目。与 GmSSL、OpenSSL 做过逐字节一致性比对，但并不隶属于这两个项目，也未获它们或任何标准机构、厂商的背书或认证。
