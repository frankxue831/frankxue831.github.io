What it is

gm-crypto-rs is a pure-Rust implementation of {% include glossary-term.html term="sm2" %} signing, encryption and key exchange (GB/T 32918), {% include glossary-term.html term="sm3" %} hashing (GB/T 32905), and {% include glossary-term.html term="sm4" %} block encryption (GB/T 32907). Its {% include glossary-term.html term="no_std" %} + alloc core builds for wasm, fits RustCrypto's digest, mac, cipher and opt-in aead 0.6 traits. The crate family exposes 112 C ABI entry points at v1.13.0.

SM4 modes include GCM, CCM and XTS. CCM encryption accepts chunks after the caller commits the plaintext length at construction; decryption accepts incremental input but buffers output until authentication succeeds. Strict-DER X.509 v3 parsing and SM2 signature verification (GM/T 0015 profile; the parser makes no trust decisions) support a TLCP toolkit for key derivation, record protection, and certificate-pair / chain verification. The caller supplies protocol state and peer-identity checks.

Not independently audited. The public tests and timing measurements below are evidence with limits, not a security certification or proof of constant-time behavior.

The public demo at its pinned commit is a consumer and smoke-test tour of hashing, signing and verification, encryption and decryption, key exchange, and encoding. It depends on gmcrypto-core = "=1.11.2"; it demonstrates that older release, not v1.13.0.

The problem

Rust already has SM2 / SM3 / SM4 implementations, and the good ones are designed for {% include glossary-term.html term="constant-time" %} secret-dependent operations. But design intent is asserted once, at review time, and then erodes quietly — a refactor, a new fast path, a dependency bump, and a timing leak slips back in with nothing to catch it. This SDK targets a combination that makes that erosion easy: byte-level GB/T conformance, a no_std / wasm core, secret-touching paths that must stay constant-time-designed across releases, and a C ABI that hands those same paths to non-Rust callers (C, C++, Go, Zig, Python). The question is how to detect timing regressions on each commit and act on them before release.

Constraints & key decisions

Measure continuously. A dudect-bencher harness exercises twenty real secret-touching paths. Sixteen block the build, generally at |τ| ≤ 0.20. CBC-decrypt fanout alone uses a 0.55 bound on EPYC 9V74 runners; all other CPUs keep 0.20. The harness reports detection events; a low statistic means no leak was detected within the measurement budget, not that no leak exists. Cost: every PR pays for measurements, and a passing gate cannot prove constant time.

Keep the gate's scope visible. The sixteen blocking paths cover SM2 scalar multiplication, sign, decrypt and key exchange; SM4 key schedule, encryption, CTR, CBC fanout, GCM / CCM decrypt, buffered GCM decrypt and XTS decrypt; encrypted-PKCS#8 decrypt; and TLCP CBC record deprotect. Four other diagnostics — two field inversions, k-class signing and HMAC-SM3 — are telemetry on PRs, with a 0.55 gross-regression sentinel nightly. noise_twin_class_split is a separate non-blocking noise diagnostic, required to appear in every run; it is not a twenty-first real secret-handling path. Cost: these measurement tiers and runner-specific noise need ongoing calibration.

A safe core; SIMD is opt-in. gmcrypto-core forbids unsafe code in its [lints] table (unsafe_code = "forbid"). The bitsliced SIMD S-box needs unsafe, so all of it is quarantined in a separate gmcrypto-simd crate behind the sm4-bitsliced-simd feature. Cost: the fast path isn't the default — you opt into SIMD, and the stock build runs the slower linear-scan S-box.

Constant-time-designed arithmetic, caveat stated. Secret-dependent arithmetic is built on subtle and crypto-bigint, and secret material is zeroized on drop via zeroize, on a best-effort basis. v1.13 extends this to the whole SM4 streaming family, including buffered payloads. The design targets constant time but can't guarantee it everywhere. Cost: on CPUs whose multiply latency is data-dependent (some older x86, some embedded), the timing properties don't hold — stated plainly under What it isn't rather than buried.

Make the core and C contracts explicit. CCM encryption commits length before accepting chunks; over-feeding poisons the encryptor, and under-feeding cannot produce a valid final tag. Decryption releases no plaintext before tag verification. The same contract crosses the C ABI, with eight new functions in v1.13. Cost: callers must know the plaintext length up front, decryption needs output buffering, and Rust and C behavior must be tested together.

Evidence

Standard KAT vectors, GmSSL 3.2.0 interoperability checks and OpenSSL 3.x SM4-XTS comparisons (xts_standard=GB) check byte identity. The public {% include glossary-term.html term="dudect" %} harness checks for timing regressions; 35 cargo-fuzz targets exercise untrusted-input decode / decrypt paths nightly. The v1.13.0 C header records the CCM contract and the 112-function surface; the tagged workflow records the runner-specific threshold and diagnostic tiers.

A timing failure held the release

The first v1.11.1 cut was held when a serial-SM4 repair exposed a TLCP CBC timing residual above the gate. Equal SM3 compression counts had concealed secret-length-dependent buffer copying and padding. The patch rewrote inner-HMAC to a fixed schedule before release. This repair applies to every tlcp-enabled build, including gmcrypto-c; default gmcrypto-core enables neither affected feature and is behavior- and timing-identical to v1.11.0. The separate serial-SM4 repair executes only with sm4-bitsliced-simd; its throughput improvement was measured on AArch64, while x86_64 has correctness / KAT / fuzz coverage but no throughput measurement. API, ABI and wire bytes stayed unchanged. The tagged repair record shows a gate changing a release decision; it does not prove constant time.

Next

No successor arc is committed to a version. AVX-512 sbox_x64 remains parked. Endpoint identity binding stays the caller's permanently; it is outside the toolkit's scope.

What it isn't

  • Not a TLS/TLCP stack — the tlcp work is a toolkit of primitives (key schedule, record protect / deprotect, chain and pair verification). There is no handshake state machine, no negotiation, and no session management: a caller drives the protocol, as the v1.9 C examples do.
  • Not endpoint authentication — verify_chain / verify_pair establish structural trust only. Binding a verified chain to a peer identity, the TLCP equivalent of hostname verification, stays the caller's permanently.
  • Not SM9, ZUC, or post-quantum.
  • Not an HSM / SDF / SKF integration.
  • Not a certified cryptographic module under the U.S. Federal Information Processing Standards (FIPS) or another certification program.
  • Not constant-time on CPUs with data-dependent multiply latencies (some older x86, some embedded).
