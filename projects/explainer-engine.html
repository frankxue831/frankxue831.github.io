Explainer Engine

Make code and technical concepts easier to see.

I want to try using animation to make relationships in code and technical concepts easier to understand, and explore how AI can help. Explainer Engine is one attempt: it starts with an explanation script, produces video with narration and captions, and checks the script’s source citations before rendering.

From script to screen

The input is a YAML {% include glossary-term.html term="storyboard" %} specifying scenes, narration and source citations—not arbitrary code uploaded for an automatically reliable explanation. This is an excerpt from the second video’s per-line beat; the frame comes from 12 seconds into the existing video.

The excerpt specifies the displayed code, the cited source line and the evidence to find; the same beat defines its curve as 2 * x. The on-screen code is a teaching view marked simplified, not a verbatim source listing. Read the full script.

  1. Check citationsThe citation gate checks whether the cited lines contain the evidence declared in the script.
  2. Generate the scene by fixed rulesThe script compiles into {% include glossary-term.html term="manim" %} scene code; no language model writes that code.
  3. Render and narrateManim renders the visuals, and a text-to-speech service synthesizes the narration. These examples also provide English and Chinese caption tracks.

Separately, the optional explainer plan uses a language model to draft a script from a selected source range. It is a preparation step: the draft must still pass the same citation gate, which checks its citations, not its narration. The model does not generate scenes during rendering.

What you can check

The second video’s script and source are at public commit c345e66. After setting up the environment as described in the repository and checking out that commit, run:

explainer verify examples/evidence-budget.story.yaml

This command checks citations; it does not re-render the video. It does not establish that the explanation is semantically correct or educationally effective.

  • The video’s storyboard
  • Evidence constants: lines 55–58
  • Budget calculation: lines 205–211
  • Weak-citation rejection: lines 312–313

The planner’s budget allows two token slots per cited line, with a floor of five and a cap of twenty-four, and the planner drops citations with fewer than two tokens or no strong token. The citation gate itself does not apply that budget; it checks the declared evidence against the cited lines. This site states that this clip was rendered from c345e66 and the third from 9a59b3f; the pictures alone do not establish that provenance. Both scripts cite their own repository without pinning a commit, so their badges read verified without a commit.

Decisions and trade-offs

Animation can make a relationship easier to see, but it can also make a wrong explanation look more convincing. The checks here constrain citations; they do not replace judgment about the explanation itself.

Stop rendering when a citation does not check out. The gate checks for declared evidence in source; when the script pins a commit, it also checks that the repository’s HEAD matches and rejects a dirty tree without explicit opt-in. Cost: Script authors must maintain resolvable citations and may need to revise them when source changes.

Keep provenance on the teaching view. The simplified label and verified badge show the gate's verdict, not a guarantee that the explanation is correct. Cost: Labels and citations take space away from the diagram and code.

Use a model to draft, fixed rules to generate code. The same script produces the same scene code through deterministic codegen; the actual video still depends on the render environment, fonts and narration resources. Cost: A new beat type requires engine changes, not just a new prompt; the planner cannot bypass the gate.

Share the render core with the desktop tool. The same Qt-free core also serves the batch-render GUI. Cost: Core changes must serve both consumers, without blocking the GUI for the convenience of the CLI.

Implementation note: sharing code is not the same decision as sharing a package

Where it stands

The source is public and the project is pre-release. The repository’s first public tag is v0.1.0 (tagged 2026-10-15, UTC); the summary below still names the older local explainer-plan snapshot, which is not that tag. No teaching outcomes have been validated. Nothing is committed to a milestone. The open question remains which relationships benefit from animation, and how to make explanations easier to understand and citations easier to check.

Limits

  • Not an arbitrary-code-to-reliable-explanation tool: the input remains an explicit script.
  • Not video improvised by an LLM during rendering: the AI planner only provides optional script drafting.
  • The diagram canvas animates relationships, but learning benefits have not been validated.
  • On-screen code is a cited teaching view, not a verbatim source viewer.
  • Citation checks do not establish semantic correctness. The badge gives a verdict; to check a particular claim, readers still need source links and evidence.
  • The earlier video’s historical verification result is not independently checkable; public source does not mean every local snapshot is published.
